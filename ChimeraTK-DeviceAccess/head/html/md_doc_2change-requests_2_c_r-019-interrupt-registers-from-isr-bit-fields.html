CR-019: Implicit interrupt registers from INTC ISR bit fields

Synopsis: The interrupts of an INTC interrupt controller can only be referred to by their numeric id. The 1-bit children of the controller's ISR register shall implicitly become interrupt registers carrying the id [<handler id>, <bit position>], so that interrupts can be referred to by name.

Status: DONE

Requirements

Aspect: interrupts derived from the ISR of an INTC controller.

  • The derivation and the parse-time validation below apply to the JSON (*.jmap) map files only. The traditional (*.mapp) parser is unaffected and keeps its current behaviour, so *.mapp fixtures with INTC entries without an ISR (e.g. tests/irq_test.mapp) continue to parse.
  • An INTC handler entry with qualified interrupt id I and controller path P makes each child register of P/ISR an interrupt register. A child qualifies when it is one 1-bit bit field of the ISR word: one channel of width 1 bit, one element, and the same bar and address as ISR.
  • The child's interrupt id is I followed by the child's bit position in the ISR word.
  • The child keeps its path, name, address, size and bit position; only its access changes to interrupt.
  • The derived registers behave like declared interrupt registers: readable with wait_for_new_data, notifying for the ISR bit the child names, part of the backend's list of interrupts, and reachable through their canonical interrupt path.
  • ISR must be a scalar register: one element, one channel, no channels dictionary. A multi-element or multi-channel ISR is an error while parsing the map file: a channel slice below ISR would be indistinguishable from a bit field, so no channels appear below ISR.
  • ISR must not be double-buffered: its BUF0/BUF1 views are children that are not bit fields, so a double-buffered ISR is an error while parsing the map file.
  • ISR either has no children at all, or only qualifying children.
  • A child that is not a qualifying bit field, i.e. a wider, multi-channel or multi-element child, or one at its own address, is an error while parsing the map file. The handler interprets ISR as one status bit per interrupt, so any other child has no defined meaning.
  • Deeper levels below ISR are not allowed: a child that has children of its own is an error while parsing the map file.
  • Every handler entry is processed, primary and nested.
  • A nested entry uses its own path and its full id.
  • Descriptor parsing and validation move to parse time for the parts the augmenter needs, which is stricter than today: a handler entry was previously interpreted only when a handler used it, so an unused entry was never validated.
  • An INTC handler entry whose P/ISR does not exist is an error while parsing the map file, for used and unused entries alike. An unused but valid entry is now merely validated rather than ignored, so it still parses; only a genuinely invalid entry, such as a missing P/ISR, makes a map that parsed before fail to parse.
  • The controller path of every INTC handler entry is read and validated at parse time, no longer only when a handler is used.
  • The option-register validation of an entry is not part of this and still runs only when a handler uses it, so an unused entry with an invalid option combination fails only then.
  • An ISR without any child is not an error and changes nothing.
  • Two children covering the same bit position are an error while parsing the map file.
  • A child of ISR that already carries interrupt access, i.e. whose register access is INTERRUPT from a declared triggeredByInterrupt, is an error while parsing the map file, even if its own id equals the derived one: an ISR child is derived, so a declared interrupt is redundant and the child's own id would be silently overwritten.
  • A derived id that is already present on a register other than an ISR child is not an error: two registers may share one interrupt id and are then notified together by the same ISR bit. Registers outside ISR are never checked.
  • An interrupt handler entry must be a JSON object and must carry exactly one controller key at its top level, once subhandler and underscore-prefixed keys are dropped. An entry with several controller keys, or one that is not an object, is an error while parsing the map file. This applies wherever the entry is read: the JSON map file parser and the metadata catalogue that carries the entry of a traditional map file.
  • The children of ISR are the registers whose path has ISR as its complete leading path components. A register that only shares the text prefix, such as P/ISR_EXTRA/READY when ISR is P/ISR, is not a child and is left untouched: it neither becomes an interrupt nor is rejected as a deeper level.
  • An ISR child whose bit position lies outside the ISR word or outside the distributor's 32-bit interrupt mask is an error while parsing the map file. The distributor maps an interrupt id to one bit of a 32-bit mask, so a position outside either range has no interrupt to notify.
  • Only the built-in INTC controller type augments the catalogue. The other built-in type, dummy, is left untouched and only reaches the metadata.
  • Augmentation is a capability of a controller type, not of INTC alone: the mechanism must let a controller type supply its own augmentation.
  • The factory offers no public way to register a further controller type yet, so only the built-in INTC augments for now. Adding that registration is deferred to a separate change request; the design assumes it will exist.

Specifications

  • Documentation: doc/jmapFormat.dox (modified).
    • The jmap_interrupts section gains a note that the 1-bit child bit fields of <path>/ISR become interrupt registers with the id [<handler id>, <bit position>], that an INTC ISR must be a scalar register without channels or deeper levels, and that an ISR child must not declare its own triggeredByInterrupt.
    • The note added above gives each rejected child shape as an error while parsing the map file, among them a child that declares its own triggeredByInterrupt. The parser rejects such a child instead of accepting it and ignoring its declared interrupt, so the note must not suggest the child is accepted.
    • The documentation also corrects the statement that the parser passes an interrupt controller entry on to the metadata verbatim without interpreting it (around line 267): an INTC entry is now interpreted at parse time to augment the catalogue, while other handler types keep the verbatim behaviour.

NumericAddressedRegisterCatalogue (modified)

Location: include/NumericAddressedRegisterCatalogue.h (modified), src/NumericAddressedRegisterCatalogue.cc (modified).

  • void modifyRegister(NumericAddressedRegisterInfo const& info) (new)
    • Replaces a register in place and keeps the insertion order.
    • It updates the derived interrupt bookkeeping first and then calls the base modifyRegister.
    • Reason: the base primitive touches neither set, so the derived registers would otherwise be missing from getListOfInterrupts() and their canonical interrupt paths would not resolve.
  • void addInterruptBookkeeping(NumericAddressedRegisterInfo const& info) (new)
    • Extracts the interrupt bookkeeping of addRegister into a private helper.
    • Both addRegister and modifyRegister call the helper, so the logic stays in one place.
    • The helper inserts the interrupt id into _listOfInterrupts and the canonical interrupt paths !I, !I:M, ... into _canonicalInterrupts.
    • The helper only inserts, so it does not support modifying a register away from interrupt access.
    • A pre-existing interrupt id is not an error: the insertion is idempotent, so two registers can share one id.
  • The derived modifyRegister hides the non-virtual base method, so callers on the concrete type also run the bookkeeping; for a non-interrupt register the helper does nothing. This mirrors the existing non-virtual addRegister override.
  • Dependencies: none new.

async::MuxedInterruptDistributorFactory (modified)

Location: include/async/MuxedInterruptDistributor.h (modified), src/async/MuxedInterruptDistributor.cc (modified).

  • Registry record (new)
    • One entry per controller type, so the existing creator and the optional catalogue augmenter share one lookup key and one registration point.
    • Replaces the _creatorFunctions map.
    • The optional augmenter is the extension point for further controller types: a type that augments supplies its own. Only the built-in INTC registers one today; a public registration API is a separate change request (see Requirements).
    • The augmenter member has this type: std::function<void(std::vector<size_t> const&, std::string const&, NumericAddressedRegisterCatalogue&)>; it is empty for a type that does not augment the catalogue.
  • Private constructor (modified)
    • Registers the built-in types: INTC with its creator and augmenter, dummy with its creator only.
  • void augmentCatalogue(std::vector<size_t> const& interruptId, std::string const& controllerType, std::string const& controllerDescription, NumericAddressedRegisterCatalogue& catalogue) (new)
    • Dispatches one handler entry to the augmenter of its controller type.
    • Looks the record up by controllerType and calls its augmenter with the id and the description.
    • An unknown type and a type with an empty augmenter are skipped, so the dispatcher is a no-op for dummy and for any type that is not registered. An unknown type stays an error at distributor creation.
    • Takes the controller type and the description as strings, so the header needs neither nlohmann::json nor the catalogue's definition; the catalogue is only forward-declared.
  • Dependencies: the augmenter of INTC and async::GenericMuxedInterruptDistributor::augmentCatalogue.

async::GenericMuxedInterruptDistributor (modified)

Location: include/async/GenericMuxedInterruptDistributor.h (modified), src/async/GenericMuxedInterruptDistributor.cc (modified).

  • static void augmentCatalogue(std::vector<size_t> const& interruptId, std::string const& controllerDescription, NumericAddressedRegisterCatalogue& catalogue) (new)
    • The augmenter MuxedInterruptDistributorFactory stores for INTC.
    • Reads path from the controller description by reusing the parsing and validation of create, so descriptor errors keep their messages and gain the handler id.
    • Descriptors of all entries are validated at parse time, no longer only when a handler is used.
    • Finds path / "ISR" in the catalogue; the separators are synonymous. A missing register throws a logic_error naming the handler id and the register.
    • A non-scalar ISR, i.e. one with several elements or with a channel layout, throws a logic_error: a channel slice below ISR would be indistinguishable from a bit field, so no channels may appear below ISR. A scalar register carries exactly one channel that spans the whole element word (bitOffset 0 and width equal to the element pitch), whereas a register declared with a channels dictionary carries one channel per named channel, whose width is the channel's own width. The check requires the single channel to span the element word, so it also rejects a channels dictionary that happens to declare exactly one channel.
    • Children are the catalogue registers whose path carries ISR as its complete leading path components and has exactly one component more. The match compares the path components, not the text prefix: RegisterPath::startsWith is a text comparison and also matches P/ISR_EXTRA/READY against P/ISR, so it would turn an unrelated register into a child or reject a valid map.
    • A register more than one path component below ISR throws a logic_error, so no deeper levels are allowed. A first pass over the registers below ISR rejects any deeper register, so the rule holds independently of the order in which the catalogue is enumerated; the second pass then validates and modifies the direct children in place.
    • A child qualifies as one channel of width 1, one element, at the same bar and address as ISR. The bit position is the channel's bit offset, which for a bit field is its representation.bitShift.
    • A child that is not such a bit field throws a logic_error.
    • A child whose bit position lies outside the ISR word or outside the distributor's 32-bit interrupt mask throws a logic_error, checked after the qualifying-child check. The bit position becomes the last element of the interrupt id, which iToMask uses as a shift amount on a 32-bit mask, so a position of 32 or more would shift its single bit out of range.
    • A qualifying child that already carries interrupt access throws a logic_error. The check is child.registerAccess == NumericAddressedRegisterInfo::Access::INTERRUPT and runs after the qualifying-child check, so a non-qualifying child keeps its own message. It is unconditional, so it also rejects a declared id equal to the derived one, and it tests the register access rather than the id, so it also holds for a named reference whose id is not resolved yet (CR-020). Registers outside ISR are not checked, so shared ids stay allowed.
    • Modified in place: a copy of the register info with interrupt access and the interrupt id, written back through the catalogue's modifyRegister.
      • Channels, address, size, bit-range flag, path and the BUF0/BUF1 views stay as they are.
    • Two children with the same bit position throw a logic_error.
    • An ISR without children returns without a change.
    • The catalogue parameter is by reference, so the header needs only a forward declaration of NumericAddressedRegisterCatalogue, not its definition.
  • Dependencies: NumericAddressedRegisterCatalogue::modifyRegister (new) and GenericMuxedInterruptDistributor::create.

getInterruptControllerNameAndDescription (new)

Location: src/JsonMapFileParser.cc (modified).

  • static std::pair<std::string, std::string> getInterruptControllerNameAndDescription( nlohmann::json const& descriptor) (new)
    • An interrupt handler entry carries exactly one controller key, so the helper reads the controller type from that single key and takes its dumped value as the description.
    • The exactly-one-key precondition is validated rather than asserted, so a malformed descriptor throws a logic_error instead of aborting an assertion-enabled build and silently picking the first key in a release build.
    • The single key is an invariant of the entry reader: it erases subhandler and drops underscore-prefixed keys, so only the controller key remains. The descriptor handed to the helper is known to be non-empty, so the validation requires exactly one key.
    • The validation is applied in both copies of the helper, the parser copy and the file-local copy in src/async/MuxedInterruptDistributor.cc. The latter reads the descriptor from the metadata catalogue of a traditional map file, so it never passes through the entry reader and its descriptor is otherwise unchecked.
    • File-local, so JsonExtensions.h stays independent of the library's use of json: only the map file parser interprets the controller descriptors. The function was previously shared through JsonExtensions.h and JsonExtensions.cc; it moved into the parser for that reason.
    • Used by detail::InterruptHandlerEntry::augmentCatalogue and by async::MuxedInterruptDistributorFactory::getInterruptControllerNameAndDescriptionFromCatalogue, which carries its own file-local copy in src/async/MuxedInterruptDistributor.cc.
  • Dependencies: none new.

Alternatives considered

  • Temporarily creating a distributor and calling a virtual augment method on it: rejected. A distributor needs a SubDomain holding a backend, and its constructor opens the ISR/IER accessors; neither exists at parse time. It would need a parent-less construction path and the backend-dependent setup moved out of the constructor.
  • Public registration of controller types (a registerDistributor template plus a base-class augmentCatalogue default): deferred to a separate change request. The registry record's optional augmenter is the extension point, so the mechanism lets a further type augment; only the public registration call is missing.
  • Requiring each controller class to carry its own name as a static member: rejected. The name is a property of the registration, and an argument keeps the controller classes free of it.
  • A second registry in the factory beside the creator functions: rejected. One record per type keeps one lookup key and one registration point.
  • Removing and re-adding a register instead of modifying it: rejected. It loses the insertion order of the iterated catalogue.
  • Augmenting at open() or lazily in the backend: rejected. The interrupt ids have to exist while the map file is parsed.
  • Excluding the BUF0/BUF1 buffer views of ISR from the child scan so a double-buffered ISR still parses: rejected. The child scan enumerates the catalogue by path component and does not special-case the buffer views, so a double-buffered ISR is an error (see Requirements).
  • Detecting a channels layout below ISR by channels.size() != 1 alone: rejected. A channels dictionary with a single channel leaves the register with one channel and one element, indistinguishable from a scalar by count. The check instead requires the single channel to span the whole element word (bitOffset 0 and width equal to the element pitch), which a scalar register always satisfies and a channels register does not, since its channel width is the channel's own width. Detecting the layout by elementPitchBits was rejected as well: a channels register may set an explicit pitch that coincides with a scalar element size, while the channel-word comparison holds in all cases.
